Where the quality really comes from

Instead of storing:

road.png
512 KB

you generate the road inside a shader.

Instead of:

building01.obj
building02.obj
...

you generate buildings from parameters like:

height
width
window count
roof type
seed

One procedural building generator can create thousands of unique buildings.

Rendering libraries I'd use

For a competition like this, I'd choose:

Option 1 (my favourite)

C++ + raylib + OpenGL

Why?

Very small executable
Fast iteration
Easy custom shaders
You still have full OpenGL access

Typical rendering pipeline:

raylib
↓
OpenGL 3.3
↓
GLSL shaders

raylib handles the windowing and input while you write the rendering techniques you need.

Option 2

SDL2 + OpenGL

Slightly more work but maximum flexibility.

Option 3

Pure OpenGL

Smallest dependency footprint, but significantly slower to develop.

How do you achieve the colours?

The secret isn't expensive textures—it's the post-processing.

A simple scene can look dramatically better with:

Tone mapping
Bloom
Colour grading
Ambient fog
Screen-space vignette
Filmic exposure
Gamma correction

These are all shader effects.

For example, bloom adds only a few hundred lines of code but can make bright highlights feel much more cinematic.

Materials without textures

Instead of using image textures, define materials procedurally:

Road:
roughness = 0.8
colour = dark grey

Metal:
roughness = 0.2
metallic = 1.0

Glass:
roughness = 0.05
transparency = 0.9

Noise functions, gradients, and triplanar mapping can add variation without storing texture files.

Character quality

You don't need a 50,000-triangle character.

A stylised runner using roughly:

1,500–3,000 triangles
flat or simple gradient colours
shader-based rim lighting

can look excellent while remaining tiny.

The city

You don't model a city.

You write a city generator.

For example:

Random seed
↓
Road network
↓
Building footprints
↓
Extrude buildings
↓
Add windows procedurally
↓
Street lights
↓
Trees

The entire city is regenerated from the same seed each run, so only the algorithm is stored.

Audio

Award-winning entries also generate audio procedurally.

Instead of shipping 40 MB of WAV files, they synthesise music and sound effects at runtime.

Could the screenshot I generated fit?

No.

If you recreated that exact scene with traditional assets, it would likely consume hundreds of megabytes.

To fit within 1.44 MB, you'd need to:

Replace detailed models with procedural geometry.
Replace textures with shader-generated materials.
Generate the city and foliage algorithmically.
Use simple, stylised lighting instead of heavy PBR assets.
Generate or synthesise audio rather than storing it.

The resulting game could still be visually striking, but it would have a cleaner, more stylised aesthetic.

If I wanted to maximise my chances of winning

I'd deliberately avoid photorealism and instead aim for a distinctive visual style.

Imagine something like:

clean low-poly geometry,
bold colour palettes,
dramatic lighting,
atmospheric fog,
bloom,
smooth animation,
procedural architecture,
and expressive shaders.

That combination is much more achievable under a 1.44 MB limit, and it also tends to stand out more than trying to imitate modern AAA graphics.

One thing worth noting: the biggest winners in size-limited competitions are often recognised not because they look like Unreal Engine games, but because they create an impressive illusion of richness using a tiny amount of data and clever procedural techniques.
