* successful games cycle:

    `Prototype → Prove Fun → Build Technology → Build Content → Polish → Optimize`

Notice that optimization comes last, not first.

* Vision Statement
  -Project Name:
    Escape

  "An adaptive procedural runner where the city learns how you play."

  - One-sentence pitch:

    `Race through a living procedural city that constantly rewrites itself while you're trying to beat your own ghosts.`

* Technology Stack

  - This is where I'd make very deliberate choices.
  | Layer           | Choice                 | Why                                              |
  | --------------- | ---------------------- | ------------------------------------------------ |
  | Language        | **C++20**              | Mature, fast, compact binaries, strong tooling   |
  | Graphics        | **raylib**             | Lightweight, simple API, OpenGL access           |
  | Rendering       | **OpenGL 3.3 Core**    | Widely supported, enough for stylized visuals    |
  | Shaders         | **GLSL**               | Tiny, expressive, procedural effects             |
  | Audio           | **miniaudio**          | Single-header, lightweight                       |
  | Math            | **raymath**            | Bundled with raylib                              |
  | Noise           | Custom Simplex/Perlin  | Small code footprint                             |
  | ECS             | Custom lightweight ECS | Avoid large dependencies                         |
  | Build           | **CMake**              | Cross-platform                                   |
  | Compiler        | **Clang** (or GCC)     | Optimize with `-Oz`/`-Os`, LTO, stripped symbols |
  | Version Control | Git                    | Standard workflow                                |
    
  - I would avoid Unreal, Unity, Godot, SDL + many extensions, Bullet Physics, and other heavy frameworks because they add complexity and binary size that aren't necessary for this design.

* Adaptive Director:
     - Rather than "AI", use a lightweight director inspired by systems like the one in cooperative shooters:
       Player slides a lot
        ↓
       Increase overhead obstacles
        ↓
      Player adapts
        ↓
      Increase road hazards
        ↓
      Player succeeds
        ↓
      Introduce new event
    - The player perceives intelligence while the implementation remains simple.


* Rendering Techniques:
    Procedural sky gradient
    Signed Distance Field (SDF) effects where appropriate
    Screen-space fog
    Bloom
    Filmic tone mapping
    Rim lighting
    Gradient materials
    Simple shadow mapping or stylized shadows (depending on budget)
    Instanced rendering for repeated geometry
  These provide strong visuals with minimal stored data.


* Procedural Audio:
  - Generate:
      Music
      Footsteps
      Wind
      Traffic hum
      UI sounds
  A small synthesizer and parameterized effects can replace many recorded assets.


* Testing Strategy:
  1. Unit tests for deterministic procedural generators.
  2. Seed-based regression tests to ensure world generation doesn't change unexpectedly.
  3. Performance profiling early and often.
  4. Daily playtests focused on "Was it fun?" rather than "Was it bug-free?"

* Final Optimization Pass:
  Only after the game is complete:
   - Remove dead code.
   - Merge similar shaders.
   - Strip debug symbols.
   - Enable Link Time Optimization (LTO).
   - Optimize for size (-Os/-Oz where supported).
   - Compress assets where allowed.
  If the contest rules permit executable packers, evaluate UPX; otherwise, skip it.
 

* Team Structure:
  Even for a solo project, I'd mentally separate the roles:
  | Role                | Primary Focus                  |
  | ------------------- | ------------------------------ |
  | Creative Director   | Protect the vision             |
  | Game Designer       | Mechanics and balance          |
  | Engine Programmer   | Rendering and systems          |
  | Gameplay Programmer | Controls and game loop         |
  | Technical Artist    | Shaders and procedural visuals |
  | Audio Designer      | Procedural sound               |
  | QA Lead             | Playability and polish         |

When one person wears all the hats, explicitly switching roles helps avoid spending weeks polishing a rendering feature before proving that the core gameplay is compelling.

One thing I'd add that many teams skip

I'd define a "Kill Test" for every milestone:
  If we removed this feature tomorrow, would players miss it?
If the answer is no, the feature doesn't belong in a 1.44 MB game.

That discipline keeps the scope tight, the binary small, and the experience focused—qualities that are often exactly what judges appreciate in size-constrained competitions.
