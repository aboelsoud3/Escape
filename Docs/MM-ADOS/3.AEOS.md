This is exactly the kind of problem where I think **agentic workflows** are more important than model choice.

Whether you use **OpenCode + Ollama**, **Claude Code**, **Codex CLI**, or another coding agent, the process should be the same.

What you want isn't:

> "Generate some markdown files."

What you want is:

> **Bootstrap an Engineering Operating System inside the repository.**

I would treat that as **Sprint -1** (before Sprint 0).

---

# The Bootstrap Phase

The repository initially contains almost nothing.

```text
pulse/

README.md
```

The AI's job is **not** to write game code.

Its only job is to build the engineering environment.

---

# Stage 1 — Bootstrap Mode

Instead of saying

> Build PULSE

tell the agent

> **Enter Bootstrap Mode**

Bootstrap Mode has only one objective:

> Prepare this repository for long-term autonomous development.

That wording changes the mindset from "coding" to "engineering."

# Stage 12 — Validate the AEOS

Before any game code is written, ask the agent to audit its own operating system.

Questions like:

* Are there missing documents?
* Is there a single source of truth for project status?
* Can a new engineer resume this project after six months?
* Does every task have acceptance criteria?
* Is there a defined session start and session end protocol?

Only after those answers are satisfactory do you move into implementation.

# If I were building this today

I would actually add **one more capability** that I think is missing from current agentic coding tools.

I would create an executable command layer inside the repository, for example:

```text
.aeos/
├── bootstrap.md
├── resume.md
├── implement.md
├── review.md
├── retrospective.md
├── release.md
└── audit.md
```

Each file describes a repeatable operating procedure rather than a conversational prompt.

Then, instead of saying:

> "Continue working on the player controller."

I'd instruct the agent with something like:

> **Run the Resume workflow, then the Implement workflow for Issue #P-003.**

Conceptually, the workflows are:

* **Resume** → Synchronize project memory, validate documentation, identify the current task.
* **Implement** → Plan, code, test, self-review, update documentation.
* **Review** → Architecture audit, performance audit, binary-size audit, maintainability audit.
* **Retrospective** → Update lessons learned, technical debt, sprint health, and risks.
* **Release** → Verify all quality gates and prepare the next milestone.

At that point, OpenCode isn't just responding to prompts—it's executing a consistent engineering process. That's much closer to how experienced software teams operate, and it scales far better as the project grows.
