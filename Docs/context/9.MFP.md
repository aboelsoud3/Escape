I like this direction. However, I'd change one thing before we write a roadmap.

As Technical Lead, I would **not** define an MVP first.

I would define an **MFP**.

> **Minimum Fun Prototype**

Many indie games fail because they build an MVP (menus, save system, settings, UI...) before proving the game is actually fun.

For **PULSE**, the roadmap should be:

```
Vision
      ↓
MFP (Minimum Fun Prototype)
      ↓
Vertical Slice
      ↓
MVP (Contest Playable)
      ↓
Alpha
      ↓
Beta
      ↓
Gold (Contest Submission)
```

# Definition of Done

Every feature must pass these gates:

| Gate          | Question                                           |
| ------------- | -------------------------------------------------- |
| Gameplay      | Is it genuinely fun?                               |
| Readability   | Can a first-time player understand it immediately? |
| Performance   | Does it maintain the target frame rate?            |
| Determinism   | Does the same seed produce the same world?         |
| Size          | How many KB did this feature add?                  |
| Replayability | Does it increase the desire for "one more run"?    |

If a feature fails **any** of these gates, it does not move to the next phase.

# One recommendation I'd make before writing a single line of C++

I would create a **Feature Scorecard**. Every proposed mechanic gets scored from 1–5 in these categories:

| Criterion          | Weight |
| ------------------ | -----: |
| Replayability      |    30% |
| Originality        |    25% |
| Development Cost   |    15% |
| Binary Size Impact |    15% |
| Technical Risk     |    10% |
| Polish Potential   |     5% |

Only mechanics with the highest weighted scores make it into the game. This prevents feature creep and ensures that every week of development moves the project closer to a polished, memorable contest entry rather than a larger but less focused one.
